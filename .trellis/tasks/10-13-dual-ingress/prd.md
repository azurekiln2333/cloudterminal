# 双入口并存：局域网中继 + 公网中继同时可用

## 背景

用户反馈原话：

> "不是。。。就不能中继服务器局域网两者都要吗怎么要选的。。"

当前 agent 是**二选一**：

- `setup.ts:23` 向导只有单选 `连接方式：1 中继服务器，2 本机局域网 [1]：`；
- `config.ts` 的 `connectionMode` 只能是 `'local' | 'remote'`；
- `main.ts` 里 `useLocalRelay` 为真时，`relayUrl` 被强制成 `ws://127.0.0.1:<port>/ws`，
  **完全不会连接公网中继**；反之选了 remote 就不起本地中继。

现实使用场景天然需要两个入口并存：

- 在家 / 同一 Wi-Fi：手机走局域网直连（`ws://192.168.x.x:8787/ws`），低延迟、不绕公网、断网也能用；
- 出门：手机走公网中继（`wss://域名/ws`）。

现状逼用户在出门前跑 `--setup` 切换模式，切换后另一个入口立即失效。这是产品缺陷，
不是必要约束。

## 技术现状（已核实，非猜测）

| 事实 | 位置 |
| --- | --- |
| relay 按 `agentId` 唯一持有 `socket`，第二条 agent 连接会踢掉第一条 | `server/src/relay/relay.ts:143-155`（`CLOSE_REPLACED = 4000`） |
| 同一 `agentId` + 相同 `secretHash` 允许重连，不会 conflict | `relay.ts:143-149` |
| `RelayLink` 构造时调用 `core.setEmitter(...)` | `server/src/agent/link.ts:52` |
| `AgentCore` 只有一个 emitter 槽位 | `server/src/agent/core.ts` |
| 本地中继用随机 `localRelayKey` 限制谁能注册到它 | `server/src/agent/main.ts:145-152` |
| 配对横幅只打印单个 `publicUrl` | `server/src/agent/main.ts:196-215` |

结论：**不能简单地起两条 `RelayLink`**。必须同时解决两件事：

1. relay 侧允许同一 agent 有多条连接（`socket` 单值 → 集合），否则公网入口和局域网入口
   会互相踢下线；
2. agent 侧 emitter 从单槽位变成 fan-out，否则第二条 link 会覆盖第一条的事件出口。

## 目标

### G1 双入口并存

- 一次启动后，agent **同时**：
  - 在本进程内运行局域网中继并监听 `0.0.0.0:<port>`（现有 `--local-relay` 行为）；
  - 若配置了中继地址，额外主动连接公网中继（现有 `--relay` 行为）。
- **局域网默认开启**：没有中继地址时也能用，用户不需要回答任何模式选择。
- **有中继地址 = 同时支持外网**：不需要额外开关，不需要重跑向导切换模式。
- 任一入口断开不影响另一个入口；各自独立重连。
- 两条路径共用同一套 agent 身份（`agentId` + `secret`）。

### G2 不破坏单入口用法

- 只配局域网（`connectionMode: 'local'`）→ 行为与今天完全一致。
- 只配公网（`connectionMode: 'remote'`）→ 行为与今天完全一致。
- 现有 `~/.cloudterminal/agent.json` 无需手工迁移即可继续工作。
- 现有 CLI 参数（`--local-relay`、`--relay`、`--relay-key`、`--port`、`--public-url`）
  语义保持向后兼容。
- 手机端、Windows 客户端不改协议即可继续工作（协议只做加法）。

### G3 配置与向导

- 配置能表达"局域网总是开 + 可选的中继地址"，不再是互斥枚举。
- 向导改为：先给局域网端口（默认，回车即用），再问是否连接中继；填了地址就双入口。
- 不再出现 `连接方式：1 中继服务器，2 本机局域网` 这种二选一的提问。
- 非交互路径可用（CLI 参数一次性表达双入口），便于脚本/后续 Windows 客户端复用。

### G4 配对与可观测性

- 配对横幅要同时展示**两个**可用入口地址，并标明哪个是局域网、哪个是公网。
- 每个入口的在线/离线状态要能分别观察（不是单一 online 布尔）。

### G5 不影响的约束（用户明确要求"不要影响到后期"）

- 不改动中继协议的核心路由语义（`msg` / `to` / `presence` 等帧格式与含义不变）。
- 不破坏手机端 `lib/models/protocol.dart` 既有解析。
- 不引入新的公网部署、付费资源或硬编码长期密钥。
- 不引入"无认证换便利"。

## 非目标（本轮不做）

- 不做端到端加密。
- 不做"多个公网中继"或"中继池/负载均衡"（本轮上限是 1 个公网 + 1 个局域网）。
- 不改 Windows 客户端 UI（该任务可能顺带受益，但不在本轮范围）。
- 不做手机端在双入口间自动择优/自动切换（手机仍由用户选择填入哪个地址）。
- 不重构 `AgentCore` 的会话管理逻辑，只改 emitter 出口的扇出方式。

## 验收标准

1. 用一条命令（或一次向导）配置"公网中继 + 局域网"双入口后启动：
   `local-relay` 监听成功，同时公网中继显示 agent online；**两者不再互相踢下线**
   （可在 relay 日志与 agent 侧状态同时确认）。
2. 关闭局域网入口（或让端口占用失败）时，公网入口保持在线并可正常收发；反之亦然。
3. 手机通过局域网地址 `ws://<LAN-IP>:<port>/ws` + 配对码可完成配对并操作终端。
4. 手机通过公网中继地址 + 配对码可完成配对并操作终端。
5. 同一 `agentId` + 同一 secret 同时从两个入口连接 relay 时，**不返回**
   `agent_conflict`，也**不**产生 `replaced` 关闭。
6. 仅配单入口时（local-only / remote-only），行为与改动前一致（有测试断言）。
7. `cd server; npm run check` 与 `npm test` 通过；新增测试覆盖：
   - relay 同 agent 多连接并存与逐条关闭的清理；
   - `AgentCore` emitter 扇出到多条 link；
   - 旧配置文件（只有 `connectionMode`）能正常加载并映射到新模型。
8. 手机端 `flutter analyze` / `flutter test` 通过（协议只做加法的情况下不应有改动；
   若有，需说明原因）。
9. `README.md` 中"方式一 / 方式二"二选一的表述更新为"可同时启用"，并说明
   配对横幅会给出两个地址。
10. 不新增公网部署、不新增付费资源、仓库中无硬编码长期密钥。

## 已定与仍需确认

已定（用户 2026-10-13 明确）：

- 双入口是**并存**语义，不是互斥枚举。
- **局域网入口默认开启**。局域网是默认路径，不需要用户做任何选择。
- **填了中继地址就自动同时支持外网**。有 `relayUrl` 就额外连公网中继；没有就只有局域网。
  用户不需要回答"二选一"，向导只问"要不要连中继"。
- 公网中继 + 局域网各一个，本轮不做多个公网中继。
- 配置模型需要向后兼容旧文件（不要求用户手改 JSON）。

仍需确认（选保守默认，不阻塞实现）：

1. 局域网端口冲突处理：端口被占用时**明确报错并提示改端口**，不静默换端口
   （静默换端口会让已经填好的手机地址失效）。
2. 是否需要在手机端显示"当前走的是局域网还是公网"：**本轮不做**（需要新增入口类型上报，
   属于加法协议；留作后续）。
